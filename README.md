# Azure サービスプリンシパル認証とVB.NET実装 まとめ

## 1. 暗号化技術の仕組み（基礎概念）

Azureの認証や通信メカニズムを理解するための基礎となる暗号技術の仕組みです。

### ① ハイブリッド暗号方式（公開鍵＋共通鍵方式）
処理が重い「公開鍵暗号」を最初だけ使い、安全に「共通鍵」を受け渡した後は、高速な「共通鍵暗号」で通信する仕組みです。

```text
【1. 公開鍵の受け渡し】
 [ クライアント ]                                       [ ☁️ サーバー ]
                                                  (あらかじめ鍵ペアを作成)
        │ ◀━━━━━━━━━━ 🗝️【サーバーの公開鍵】 ━━━━━━━━━━━│

【2. 共通鍵の暗号化と送信（クライアント側）】
 [ クライアント ]
  ⭐ 通信用の「🔑 共通鍵」を新しく作る
        │
        ▼
   🗝️【サーバーの公開鍵】で「🔑 共通鍵」を暗号化（箱に入れてロック！）
        │
        ▼
   📦🔒 [ 暗号化された共通鍵 ] ━━━━━━(送信)━━━━━━▶

【3. 共通鍵の復号（サーバー側）】
                                                      [ ☁️ サーバー ]
                                            ◀━━━━ 📦🔒 [ 暗号化された共通鍵 ]
                                                              │
                                                              ▼
                                            🔑【サーバーの秘密鍵】で箱をアンロック
                                            （世界でサーバーしか開けられない）
                                                              │
                                                              ▼
                                                       「🔑 共通鍵」をゲット！

【4. 安全で高速な通信の開始】
 [ クライアント ]                                       [ ☁️ サーバー ]
    (持っている)                                          (持っている)
     🔑 共通鍵                                             🔑 共通鍵
        │                                                     │
        │ ◀━━━━ (以降、「🔑 共通鍵」を使ってお互いに暗号化通信) ━━━━▶ │
```

*   **どこで使われているか:** SSL/TLSにおいて、最初の認証（鍵の受け渡し）時に「公開鍵暗号」が使われ、認証が完了した後の実際のデータ送受信では「共通鍵暗号」が使われます。
*   **なぜ2つの方式を組み合わせるのか？:** 最初から最後まで「公開鍵暗号」だけで通信すれば安全ですが、計算が複雑で処理に時間がかかりすぎてしまいます。そのため、最初の「共通鍵の受け渡し」という最も盗まれやすい一瞬だけを公開鍵暗号でガッチリ守り、無事に渡せた後は処理が速い共通鍵暗号に切り替えて通信を行っています。

### ② デジタル署名
公開鍵暗号方式を「逆」に使った仕組みです。「秘密鍵」でデータを暗号化（署名）し、相手が「公開鍵」で復号（検証）することで、「間違いなく本人が送ったこと」と「データが改ざんされていないこと」を証明します。

```text
[送信者]                                                                        [受信者]
 データ ──(ハッシュ化)──> ハッシュ値 (A)                                      データ ──(ハッシュ化)──> ハッシュ値 (B)
                           │                                                                            │
                       (送信者の秘密鍵で暗号化)                                                         │ (比較して一致すれば正当)
                           ▼                                                                            ▼
                       【デジタル署名】 ──────────────(送信者の公開鍵で復号)─────────────> ハッシュ値 (A')
```
*   **どこで使われているか:** 今回の `.pem` / `.pfx` 証明書を使ったAzureへの認証手続きや、Azure（Entra ID）から返却される「アクセストークン（JWT）」の改ざん防止検証に利用されています。

### ③ デジタル証明書と認証局（CA）の仕組み
上記①の公開鍵や②のデジタル署名を組み合わせ、通信相手が「間違いなく本物であること」を第三者が保証する仕組みです。

```text
【1. サーバー証明書の発行依頼とアップロード（事前準備）】

  [ ☁️ サーバー運営者 ]
      │ 
      │ 「証明書を作って！」と依頼（自分の公開鍵や身元情報を提出）
      ▼
  [ 🏢 認証局 (信頼できる第三者) ] ◀ 例：警察署やパスポートセンター
      │ 
      │ 審査後、🔑【認証局の秘密鍵】で実印を押す（デジタル署名）
      ▼
 📜 [ サーバー証明書 ] (PEMファイルなどの形式)
  ├── 🗝️ サーバーの公開鍵
  ├── 🏢 サーバーの身元情報 (URLや企業名)
  └── ✍️ 認証局のデジタル署名

      │ (作ってもらった証明書をサーバーにアップロードして設定する)
      ▼
  [ ☁️ サーバー (Webサイト) ]


【2. 通信時の証明書の確認（あなたがアクセスした時）】

  [ 💻 クライアント (ブラウザ) ]                       [ ☁️ サーバー ]
        │                                              │
        │ ◀━━━━ (通信開始時に証明書を提示) ━━━━━ 📜 [ サーバー証明書 ]
        ▼
 🔍 ブラウザの内部チェック
 ブラウザやOSには、最初から世界中の
 「🏢 認証局の公開鍵（確認用の合鍵）」が
 たくさん組み込まれています。

 📜証明書の「✍️デジタル署名」を、
 最初から持っている【認証局の公開鍵】で開いてみる。
        │
        ▼
 🔓 無事に開いた！ ＝ 「間違いなく本物の認証局が保証している！」
        │
        ▼
 ✅ 「このサーバーは本物だ！」と信用し、
    証明書に入っていた「🗝️サーバーの公開鍵」を取り出して、
    安全な暗号化通信（SSL/TLS）をスタートする。
```
*   **どこで使われているか:** WebブラウザがHTTPSサイトにアクセスする際の安全確認や、Azure（Entra ID）がサービスプリンシパルから送信された証明書を受け取った際、「これは間違いなく登録されたアプリからのアクセスだ」と信頼してアクセストークンを発行するプロセスで利用されています。

**【補足1】サーバー証明書はどこに設置するのか？**
*   **レンタルサーバー（PaaS/ホスティング）の場合:**
    コントロールパネル（管理画面）から証明書ファイルをアップロードするだけで、プロバイダ側が裏側のWebサーバーに自動設定してくれます。最近は管理画面のボタン一つで無料証明書を自動発行・自動更新してくれる機能も標準的です。
*   **自前サーバー（オンプレミス・IaaS・VPSなど）の場合:**
    サーバーのOSやWebサーバーソフト（Apache, Nginx, IISなど）の所定の場所に自分で配置します。例えばLinuxなら `/etc/ssl/` などのディレクトリにファイルを置き、設定ファイルにそのパスを記述します。Windows Server（IIS）の場合は、先ほどVB.NETで利用した「証明書ストア」にインポートして紐づけます。

**【補足2】認証局（CA）にはどんな企業・機関があるのか？**
*   **商用（有料）の認証局:**
    *   **DigiCert（デジサート）、GlobalSign（グローバルサイン）など:** 企業が実在するかどうかの厳しい審査（登記簿の確認など）を行ってから発行する証明書（EV証明書など）を扱います。金融機関や大企業のコーポレートサイトなどでよく使われます。
*   **無料の認証局:**
    *   **Let's Encrypt（レッツエンクリプト）:** 非営利団体が運営しており、プログラム（bot）からの申請だけで誰でも無料で証明書を発行・自動更新できる画期的な仕組みです。現在は個人のブログから一般企業のサイトまで、世界中で最も普及しています。
*   **社内専用（プライベートCA）:**
    自社内の Active Directory (AD CS) などを使って構築する「社内ネットワークだけで通用する自前の認証局」です。社内の業務用PCのOSにはあらかじめこの自前認証局の公開鍵を仕込んでおくことで、社内システムへの安全な接続を確立します。

**【補足3】ブラウザでの証明書の確認方法（例：任天堂の公式サイト）**
私たちが普段使っているブラウザ（ChromeやEdgeなど）で、実際にサーバー証明書の中身を確認することができます。

1. **サイトにアクセス**: ブラウザで対象のサイト（例：任天堂の公式サイト `[https://www.nintendo.co.jp/](https://www.nintendo.co.jp/)`）を開きます。
2. **アドレスバーを確認**: URLの左側にある「🔒（鍵マーク）」または「調整アイコン（ツマミのマーク）」をクリックします。
3. **証明書メニューを開く**: 「この接続は保護されています」という項目を選び、さらに「証明書は有効です（または証明書のアイコン）」をクリックします。
4. **中身を見る**: 証明書ビューアが開き、以下の情報が確認できます。
   * **発行先 (Issued to)**: `Nintendo Co., Ltd.` などの企業名。これで本物の任天堂のサイトであることが証明されます。
   * **発行者 (Issued by)**: `GlobalSign` など、この証明書を保証している認証局（CA）の名前。
   * **詳細タブ**: このタブを開くと、今回VB.NETのコードで扱った「拇印（Thumbprint）」や「公開鍵」の実際のデータも見ることができます。

### ④ 【要約】2つの技術の目的と証明書（PEMファイル）の関係
ここまで解説した暗号化とデジタル署名は、目的は異なりますが「証明書」という一つの仕組みの中で一緒に動いています。

*   **ハイブリッド暗号方式の目的:** 通信の**傍受を防ぐ**（中身を隠す）。
*   **デジタル署名の目的:** 間違いなく**本人であること**を確認する（なりすましを防ぐ）。

Azure CLIで証明書を作成した際に出力される `PEM` ファイルには、この2つの目的を果たすためのデータがひとまとめに入っています。

```text
-----BEGIN PRIVATE KEY-----
(あなただけが持つ「秘密鍵」。デジタル署名を作ったり、暗号化された共通鍵を開けるために使う)
-----END PRIVATE KEY-----

-----BEGIN CERTIFICATE-----
(みんなに提示する「証明書」。あなたの「公開鍵」と「認証局のデジタル署名」が入っている)
-----END CERTIFICATE-----
```

## 2. サービスプリンシパルの作成と権限付与
プログラムがAzureリソースにアクセスするための「サービスプリンシパル（アプリの身分証）」を作成します。

**【実行環境に関する重要ポイント】**
コマンドの実行には以下の2つの方法がありますが、**Azure Portal上の Cloud Shell の利用が推奨**されます。
*   **Azure Portal上の Cloud Shell (Bash) [推奨]:** ブラウザ上で完結するため、必要なツールがすべて揃っています。**何もインストールせずにそのまま実行できる**ため最も簡単です。
*   **ローカルPC (PowerShell等):** ローカル環境で実行することも可能ですが、事前に「Azure CLI」のモジュールをダウンロードしてインストールしておく手間がかかります。

**実行コマンド (Azure CLI):**
```bash
az ad sp create-for-rbac --name "FabricSyncApp" --role "Contributor" --scopes "/subscriptions/<サブスクリプションID>/resourceGroups/<リソースグループ名>" --create-cert
```
*   セキュリティの観点から、`--scopes` で対象の特定リソースグループやストレージに範囲を絞り、最小限の権限（`--role`）を付与する設計が推奨されます。
*   `--create-cert` オプションにより、Azure上に公開鍵が自動登録され、手元に秘密鍵を含む `.pem` ファイルが出力されます。

## 3. 証明書の形式変換（PEM から PFX）
VB.NET（.NET Framework 4.7.2）で証明書を扱うには、出力された `.pem` ファイルをパスワード付きの `.pfx` 形式に変換する必要があります。

**【OpenSSLの実行環境に関する重要ポイント】**
変換には `openssl` というコマンドを使用しますが、OS標準機能ではないため環境に注意が必要です。
*   **Azure Cloud Shell (Bash) [推奨]:** すでにOpenSSLが組み込まれているため、以下のコマンドを**そのまま実行するだけで変換可能**です。
*   **ローカルPC:** Windows標準のコマンドプロンプトやPowerShellには `openssl` が入っていません。「Git Bash」などのツールを別途インストールして、OpenSSLが使える環境を用意する必要があります。

**変換コマンド (OpenSSL利用):**
```bash
openssl pkcs12 -export -out FabricSyncAppCert.pfx -inkey tmpXXXX.pem -in tmpXXXX.pem
```

## 4. 認証方式の検討：証明書 vs クライアントシークレット
*   **証明書方式（Thumbprint利用）:**
    Windowsの「証明書ストア」にPFXをインストールし、コードからは「拇印（Thumbprint）」のみを呼び出します。ソース漏洩に強いですが、複数端末に配布するツールの場合、端末ごとのインストールや期限更新の保守コストがかかります。
*   **クライアントシークレット方式:**
    パスワード文字列（シークレット）を用いて認証します。端末ごとの証明書管理が不要になるため、今回のような社内限定・タスクスケジューラ無人実行ツールの場合は、保守性を優先してこちらの方式を採用することに決定しました。

## 5. クライアントシークレット方式の実装と安全な構成管理
シークレット漏洩を防ぐため、`App.config` の外部ファイル参照機能を利用し、設定値を分離します。

**① App.config (プロジェクト内・Git管理対象)**
公開可能なIDのみを記載し、シークレット用の設定ファイルを外部参照します。
```xml
<?xml version="1.0" encoding="utf-8" ?>
<configuration>
  <appSettings file="secret.config">
    <add key="ClientId" value="アプリのID" />
    <add key="TenantId" value="テナントのID" />
  </appSettings>
</configuration>
```

**② secret.config (ビルド先ディレクトリ・Git管理外)**
パスワードのみを記載し、`.gitignore` でリポジトリから除外します。このファイルをexeと同じフォルダに配置します。
```xml
<appSettings>
  <add key="ClientSecret" value="Azureで発行したシークレット文字列" />
</appSettings>
```

## 6. VB.NET 4.7.2 での実装コード (MSAL.NET)
`Microsoft.Identity.Client` (MSAL.NET) を使用してアクセストークンを取得し、TOM (Tabular Object Model) のXMLAエンドポイント接続に利用する実装です。

```vb
Imports Microsoft.Identity.Client
Imports System.Threading.Tasks
Imports System.Configuration

Public Class FabricAuthenticatorSecret
    Public Async Function GetAccessTokenAsync() As Task(Of String)
        ' App.config / secret.config から自動マージされた設定を読み込む
        Dim clientId As String = ConfigurationManager.AppSettings("ClientId")
        Dim tenantId As String = ConfigurationManager.AppSettings("TenantId")
        Dim clientSecret As String = ConfigurationManager.AppSettings("ClientSecret")

        ' 機密クライアントを構築
        Dim app As IConfidentialClientApplication = ConfidentialClientApplicationBuilder.Create(clientId) _
            .WithTenantId(tenantId) _
            .WithClientSecret(clientSecret) _
            .Build()

        ' Microsoft Fabric / Power BI XMLAエンドポイント用のスコープ
        Dim scopes As String() = {"https://analysis.windows.net/powerbi/api/.default"}

        Try
            Dim authResult As AuthenticationResult = Await app.AcquireTokenForClient(scopes).ExecuteAsync()
            Return authResult.AccessToken
        Catch ex As MsalServiceException
            Throw New Exception($"トークン取得エラー: {ex.Message}", ex)
        End Try
    End Function
End Class
```
